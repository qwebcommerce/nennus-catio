## Top defects (by severity)
1. **PO over-receipt race (FR-96/98, NFR-23).** Create a PO for qty 10, send it, then fire 6 parallel `POST /api/purchase-orders/:id/receive {lines:[{id,quantity:10}]}`. Two return 200: stock +20, two bills for 2× the cost, line shows received 10.
2. **Stock changes without a movement (FR-17, Movement only; T3's finding confirmed).** `PATCH /api/inventory/:p/:b {quantity:77777}` returns 200 with no StockMovement and no audit row. The product edit form calls it on every save. The same happens with `POST /api/inventory/reconcile`, product `initialStock`, and supabase sync. There is no ADJUSTMENT-with-reason path at all.
3. **Legacy purchase receive bypasses bill, movement and cost (Receipt raises a bill).** `POST /api/purchases/receive {branchId,supplierId,items:[{productId,quantity:10,unitCost:2}]}` returns 201: Inventory +10, 0 movements, 0 SupplierBill rows. It is live in Purchases.jsx.
4. **Website oversell of reservations (NFR-06).** 12 parallel `POST /api/shop/checkout` for 10 units each with 50 on hand all return 201, holding 120 units. Paying customers past 50 hit a 409 at the webhook, and their order stays unpaid and pending.
5. **No DB-level data rules (NFR-23).** There are zero CHECK constraints and zero triggers. Negative stock, over-received lines, overpaid bills and illegal status changes are all accepted by Postgres.
6. **Variant low-stock missing (FR-92).** There is no way to set a variant's low-stock level per location, and the dashboard returns only a count.
7. **Inactive-variant bypass and parallel product-level stock and price (FR-18, One variant).** Deactivate all variants, then a POS sale without variantId sells at Product.price from product-level Inventory. Wholesale price is a second selling price.
8. **Plan cap of 3 locations, and inactive locations accepted for transfers and POs (FR-89).**
