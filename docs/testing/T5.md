# T5 — Grooming, Relocation, Customers, Booking/Relocation rules, NFR-04, NFR-18

How it was tested: live API on :4000 for staff routes and customer relocation. Grooming `/book` and the SkipCash webhook were tested on my own server copy (:4105, same DB, `SKIPCASH_API_URL` pointed at a local mock on :4106) because `/book` calls SkipCash before it returns. Webhooks were signed with HMAC using `test-webhook-key`. Scripts are in `scratchpad/tests/T5/` (booking.mjs, conc.mjs, pay.mjs, more.mjs, staff.mjs, reloc.mjs, cust.mjs). Test data uses the T5- prefix: two customers t5-alice / t5-bob @example.test, packages T5-Basic and T5-Full, a Wednesday schedule from 09:00 to 12:00 Qatar time with capacity 1, and area T5-Area. During testing the org homeVisitFee was set to 30. Afterwards it was reset to 0 and leftover T5 holds were cancelled.

## Top defects (by severity)

1. **Grooming slots double-booked under concurrency (FR-48/50, rule Booking).** Repro: create a capacity-1 schedule, then fire 20 parallel `POST /api/shop/grooming/book` calls with the same `startAt/endAt`. All 20 return 201 and 20 PENDING_PAYMENT holds exist for one seat. Each one can be paid and confirmed. Cause: the count-then-insert at groomingShop.js:212-273 has no transaction or lock.
2. **Booking and relocation confirmed without full payment (FR-51, FR-64).** The SkipCash webhook branches for `booking:` and `relocation:` never compare `Amount` (shop.js:898-931). A signed webhook with `Amount:"1.00"` confirmed a 100 QAR booking and marked an 800 QAR relocation PAID. Separately, staff `PATCH /api/appointments/:id {"status":"CONFIRMED"}` confirms an unpaid PENDING_PAYMENT booking.
3. **Stored XSS and unchecked files (NFR-18, FR-66).** A customer submits a relocation document `{mime:"text/html", dataBase64:<script>…}`. It is stored and served as `text/html` inline. The staff RelocationDesk opens it as a same-origin blob, so the script can read the staff JWT. Product image upload accepts any bytes labelled image/png, and nothing is normalised.
4. **No status-transition rules or hours check on the staff calendar (FR-53/54).** `PATCH /api/appointments/:id` accepts DONE→CONFIRMED, CANCELLED→IN_PROGRESS, →PENDING_PAYMENT/BOOKED, and moves to times outside the schedule. Staff `POST /api/appointments` ignores slot capacity. The calendar day is UTC, so bookings between 00:00 and 03:00 Qatar time land on the wrong day.
5. **Booking time and cancel rules missing (FR-48/52/55).** `/book` accepts past dates, any `endAt` (1 minute for a 60-minute package), off-grid starts, and ends after closing. The customer can cancel a CONFIRMED booking at any time, including after it happened, with no refund. A success webhook that arrives after the hold sweep is silently ignored, so the customer is charged with no booking. There is no booking refund path at all.
6. Relocation cash or bank payment writes no payment or audit record (no amount, no reference, no user). PAID→CANCELLED is allowed with no refund.
7. FR-49 home-visit note not collected. FR-70 has no customer filter beyond text search. FR-47 has no package edit or deactivate endpoint. FR-68 record lists are truncated at 20.
